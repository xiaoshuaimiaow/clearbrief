项目背景

公司内部文档分散在不同系统中，新员工和运营同事经常需要询问他人才能找到会员政策、流程制度和项目资料，造成重复沟通和信息查找成本。

问题定义

当前需求的关键问题不是“缺一份文档”，而是项目启动前没有把用户、范围、权限、指标和兜底机制问清楚。

目标用户

新员工、运营同事、客服同事、产品团队和知识库管理员。

产品目标

帮助员工用自然语言快速查找内部知识，并在答案中展示来源，减少重复咨询，提高新人上手效率。

MVP 范围

  • 支持自然语言提问，并返回带来源引用的答案。
  • 首期接入制度文档、会员政策、产品资料和项目 SOP。
  • 提供低置信度提示，引导用户查看原文或提交人工反馈。
  • 支持按部门和文档类型配置基础访问权限。

核心流程

  1. 用户提交业务问题、会议纪要或反馈片段。
  2. 系统识别问题类型、受影响用户和方案风险。
  3. 产品经理确认关键取舍，生成 PRD 和评审材料。

跨部门待确认

  • 研发：来源引用、权限过滤和低置信度兜底的实现方案。
  • 设计：答案页、未命中页、反馈入口和来源展示的关键状态。
  • 数据：查找时间、重复咨询量、答案采纳率和未命中率的埋点口径。

竞品分析

对比 Notion AI、飞书文档、腾讯文档智能助手和 Confluence，明确 ClearBrief 的差异化是“项目启动与需求评审工作流”，而不是单纯文档生成。

数据指标

核心指标包括平均查找时间、答案采纳率、未命中率、重复咨询量和反馈处理时长。

数据口径

  • 事件表：knowledge_question_log
  • 核心字段：answer_status、feedback、answer_time_seconds、source_click、no_match_rate
  • 复盘维度：日期、用户角色、来源渠道和处理状态。

风险兜底

  • 信息不完整时不直接进入开发排期。
  • 异常状态需要明确提示和人工处理入口。
  • 上线前确认权限、数据口径和验收负责人。

验收标准

用户可以在 3 步内完成提问并查看答案来源；低置信度回答必须提供查看原文和提交反馈入口。

方案检查项与结论

方案检查项

这里不做抽象打分，而是看每一项是否会影响方案进入下一阶段。

问题价值基本成立

资料难找影响新人上手和运营效率，问题真实；还需要补充量化损失和优先级。

方案取舍方向明确

先做文档治理和搜索优化，再试点 AI，避免一上来做高成本全量改造。

风险可控待校验

权限、敏感内容、低置信度回答和人工反馈还需要明确规则、负责人和验收标准。

MVP 收敛已有边界

首期范围基本收敛，但仍需写清楚哪些 AI 能力不在本期做。

投入产出需确认

文档治理需要运营投入，AI 试点需要研发和成本评估，需要确认投入是否匹配收益。

方案结论

当前推荐路径具备进入原型和技术预研的基础，但还不建议直接进入开发排期。排期前需要验证搜索优化的效果、权限边界和 AI 试点成本。

结论：带条件通过

推荐先推进“文档治理 + 搜索入口优化”的 MVP，同时小范围验证 AI 问答，不做全量 AI 知识库。

数据分析

上线后指标看板

指标定义用途
平均查找时间从进入搜索到点击答案来源的平均时长衡量效率提升
答案采纳率用户点击“有帮助”的问答占比衡量答案质量
未命中率未返回有效答案的问题占比发现文档缺口
重复咨询量运营群内重复提问次数衡量协作成本下降
SELECT DATE(created_at) AS dt, COUNT(*) AS question_cnt, AVG(answer_time_seconds) AS avg_find_time, SUM(CASE WHEN feedback = 'helpful' THEN 1 ELSE 0 END) * 1.0 / COUNT(*) AS helpful_rate, SUM(CASE WHEN answer_status = 'no_match' THEN 1 ELSE 0 END) * 1.0 / COUNT(*) AS no_match_rate FROM knowledge_question_log WHERE created_at >= CURRENT_DATE - INTERVAL '14 day' GROUP BY DATE(created_at) ORDER BY dt;
